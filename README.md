# 社畜人设卡 · Shachiku Persona Card

> 一个基于麦当劳 MCP 的轻量 Skill：先给你定一个「今日人设」，再用**当场真实可售的菜单**配一份饭，最后**实时核价**，出一张能截图发朋友圈的卡。

```
🎴 今日人设卡  No.SC-20261021-0931
──────────────────────────────
今日人设：加班狗 🌙
「今天的你只想快点填饱肚子」

推荐：猪柳蛋麦满分套餐
价格：¥26.50（已实时核验）
门店：麦当劳汕头东厦壹佰餐厅
时段：早餐 · 2026-10-21 09:41
──────────────────────────────
```

## 目标用户

在写字楼里上班、每天至少一次「吃什么」决策、又不想在这件事上花脑力的人。典型场景是午休
前 10 分钟、加班到晚上 9 点、以及「今天想省点钱」但又懒得比价的时候。不需要懂技术，也不
需要自己配算法——抽一张卡，照着点。

---

## 它解决什么

中午 11 点，打开外卖软件，翻了三分钟菜单，最后点了一个和上周三一模一样的东西。

点餐难的不是"没有选择"，是"选择太多 + 懒得决定"。这个 Skill 把决策拆成两步：

1. **先认领一个人设**（加班狗 / 预算战士 / 热量焦虑党 / 快乐复读机 …）——这比"你想吃什么"好回答得多
2. **人设替你决定吃什么**，并且这个决定落在真实门店、真实菜单、真实价格上

人设是玩梗，但推荐是真的。

## 两种模式

| 模式 | 用户怎么说 | 系统怎么做 |
|------|-----------|-----------|
| **Roll** | 「roll 一个人设」「抽一个」「今日人设」 | 按时段加权随机抽人设（早餐时段更容易抽到早餐战士，深夜更容易抽到深夜程序员） |
| **点餐** | 「我想吃麦满分和薯条」「今天想省钱」「有没有低卡的」「三个人拼单」 | 关键词匹配人设；用户点名的餐品优先保留，再补齐搭配 |

## 快速开始

### 离线 demo（不需要 Token、不需要 MCP）

```bash
cd shachiku-persona-card

python3 scripts/demo_run.py                    # 随机 roll 一个
python3 scripts/demo_run.py --persona cheat_day
python3 scripts/demo_run.py --mode order --text "今天想省钱"
python3 scripts/demo_run.py --all              # 12 个人设各出一张，验收用

python3 scripts/gallery.py                     # 一页看完 12 张卡（推荐先看）
python3 scripts/gallery.py --menu tests/fixtures/lunch_menu_raw.json --period 午餐
```

产出在 `out/`：`card.txt` / `card.html` / `card.svg` / `card.json`。

### 真实模式（需要麦当劳 MCP）

1. 申请 Token：麦当劳 MCP 官网登录 → 控制台 → 激活 → 复制 Token
2. 把 `mcp-config.example.json` 里的 `${MCD_MCP_TOKEN}` 换成你的 Token，配到连接器的自定义
   MCP 里（WorkBuddy：左侧边栏【专家·技能·连接器】→【连接器】→ 自定义连接器 → 配置 MCP）
3. 按 `SKILL.md` 的流程走：
   `now-time-info` → `query-nearby-stores` → `query-meals` → 选人设 → `persona_engine.py pick`
   → `calculate-price` → `make_card.py` → `card.py`

```bash
# 不写 Token、不联网也能跑的那部分
python3 scripts/persona_engine.py list                       # 看 12 个人设
python3 scripts/persona_engine.py match --text "今天想省钱"    # 关键词 → 人设
python3 scripts/persona_engine.py pick --persona overtime_dog \
        --menu tests/fixtures/lunch_menu_raw.json --period 午餐   # 人设 → 选餐
```

## 四个设计决策

### 1. 人设不写死 SKU，只描述「需求特征」

初版是想让「加班狗」直接推荐「板烧鸡腿堡三件套」。开发时实测 09:32 调 `query-meals`，返回的**只有早餐菜单**——没有巨无霸，没有薯条。

麦当劳菜单按时段下发是硬约束。所以人设改成描述抽象特征：

```json
"prefer": { "burger": 0.9, "fried": 0.7, "drink": 0.6, "combo": 0.5, "combo3": 0.4 }
```

选餐时拿这些权重去打分**当场返回的每一个餐品**，任何时段都有解，换门店也不用改配置。

### 2. 套餐和单品拼配是两条路

- 「加班狗要三件套」→ 走 `combo`，直接选一个套餐产品
- 「放纵日要主食+炸物+甜品」→ 走 `compose`，逐槽位挑单品

`compose` 有三条防呆：同一角色不重复（不会出现两份主食/两份饮料）、套餐不占单品位、已有饮料不再加第二杯。这三条都是实测踩出来的——第一版给「热量焦虑党」拼出了「纯悦 + 纯牛奶」，两瓶水。

### 3. 价格必须核价，且必须解释差异

这是整个项目最容易被投诉的地方。

实测：菜单 `currentPrice` = **¥15.90** 的「猪柳蛋麦满分套餐」，`calculate-price` 返回 **¥26.50**。因为 ¥15.90 是「随单购早餐卡」价，需要额外买卡才成立。

所以卡面严格区分三种价格来源：

| 来源 | 卡面标注 | 含义 |
|------|---------|------|
| `calc` | ✓ 价格已实时核验 | `calculate-price` 成功 |
| `menu` | ! 菜单价 · 尚未核价 | 接口失败，只是菜单价 |
| `demo` | ○ 示例数据 · 非实时 | 离线 demo |

菜单价与实付不一致时，卡面会加一行：「菜单显示 ¥15.90 属随单购/会员专享价，实付 ¥26.50，以核价为准」。单项价也用核价返回的分项小计覆盖，避免出现"单项 15.90、合计 26.50"这种自相矛盾的卡。

### 4. 全流程可解释

每个推荐都带 `reasons`：`猪柳蛋麦满分套餐：主食扎实(+0.9)、套餐形态(+0.5)、完整三件套(+0.4)`。卡面写"为什么是它"，用户能看懂算法在干什么，不满意也知道该怎么调（"再 Roll 一次"不是唯一出路）。

## 分工：谁做什么

| 环节 | 谁做 | 为什么 |
|------|------|--------|
| 调 MCP（门店/菜单/核价/下单） | Agent | 只能通过 MCP 工具调用 |
| 人设匹配、选餐打分 | Python | 确定性、可测试、可解释；避免 LLM 每次给不同答案 |
| 组装 + 渲染卡片 | Python | 同上，且要保证价格标注不出错 |
| 文案润色、追问、解释 | Agent | 需要语言能力 |

一句话：**判断和算术交给代码，说话交给模型。**

- 人设库完整性（12 个、id 唯一、字段齐全、枚举合法）

## 已知限制

1. **菜单价可能不是实付价**。已用 `calculate-price` 兜底，但用户看到的"菜单价"和"实付"仍可能不同——卡面已解释，但不改变这个事实。
2. **低卡只能近似**。「热量焦虑党」在早餐时段实际只能推玉米杯 + 纯悦，因为菜单里没有真正低卡的主食。这个已写进人设 tips，如实告知而不是硬凑。
3. **门店靠用户确认**。MCP 按收藏/搜索返回门店，距离字段都是 0，无法真正排序"最近"。
4. **人设文案是固定池**（每人 3 条），Roll 多次会重复。要真正的多样性得接 LLM 生成，但那样价格标注和选餐就不稳了，所以没做。
5. **下单需人工确认**。设计上不自动下单。
